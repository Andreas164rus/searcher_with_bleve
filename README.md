# Личный поисковик по учебному хаосу

Локальный поисковый сервис на Go. Приложение рекурсивно обходит заданную директорию, индексирует текстовые документы и исходный код, предоставляет HTTP API для поиска и автоматически обновляет индекс при изменениях файлов.

Проект использует:

- Go;
- Bleve как локальный полнотекстовый индекс;
- fsnotify для событий файловой системы;
- стандартный `net/http` для API.

## Быстрый запуск

```bash
go run ./cmd/searcher -config config.json
```

По умолчанию `config.json` индексирует папку `./sample-data`, а HTTP API запускается на `:8080`.

Проверка:

```bash
curl "http://localhost:8080/search?q=scheduler"
curl "http://localhost:8080/stats"
```

Интерактивная документация API:

```text
http://localhost:8080/docs/
```

## Конфигурация

Пример находится в `config.json`.

```json
{
  "address": ":8080",
  "rootDir": "./sample-data",
  "indexPath": "./data/index",
  "supportedExtensions": [".txt", ".md", ".go"],
  "ignoredDirectories": [".git", "node_modules", "vendor", ".idea", "bin", "data"],
  "maxFileSizeBytes": 10485760,
  "defaultLimit": 10,
  "maxLimit": 100,
  "debounceMs": 300,
  "updateQueueSize": 128,
  "updateWorkers": 2
}
```

Основные параметры:

- `rootDir` - директория, которую нужно индексировать.
- `indexPath` - путь к индексу Bleve на диске. Эта папка стирается только если в ней индекс Bleve.
- `supportedExtensions` - расширения файлов, которые можно индексировать.
- `ignoredDirectories` - директории, в которые сканер и watcher не заходят.
- `maxFileSizeBytes` - максимальный размер одного файла.
- `defaultLimit` и `maxLimit` - ограничения количества результатов поиска.
- `debounceMs` - задержка для группировки повторяющихся событий файловой системы.
- `updateQueueSize` - размер очереди обновлений индекса.
- `updateWorkers` - количество workers для обработки обновлений.

## Что индексируется

Минимально поддерживаются:

- `.txt`
- `.md`
- `.go`

Файлы других форматов игнорируются. PDF, изображения, видео, архивы и бинарные файлы не разбираются.

Символические ссылки игнорируются. Скрытые файлы не имеют отдельного запрета: если расширение поддерживается и файл не находится в ignored-директории, он может быть проиндексирован.

## HTTP API

OpenAPI-описание находится в `openapi.yaml`. Во время работы сервиса оно доступно по адресу:

```text
http://localhost:8080/openapi.yaml
```

Swagger UI доступен по адресу:

```text
http://localhost:8080/docs/
```

В проекте выбран ручной OpenAPI-файл, а не генерация из комментариев. Для этой задачи это проще: API небольшой, все ручки явно описаны в одном файле, а на защите можно показать Swagger UI почти так же, как `/docs` в FastAPI.

### GET `/search`

Ищет документы по содержимому.

```bash
curl "http://localhost:8080/search?q=goroutine&limit=10"
```

Пример ответа:

```json
[
  {
    "id": "notes.txt",
    "path": "notes.txt",
    "name": "notes.txt",
    "fragment": "Go scheduler executes <mark>goroutines</mark>.",
    "score": 0.42
  }
]
```

### GET `/stats`

Возвращает состояние индекса.

```bash
curl "http://localhost:8080/stats"
```

Пример ответа:

```json
{
  "documents": 3,
  "indexedBytes": 242,
  "lastUpdate": "2026-10-04T10:20:00Z"
}
```

### POST `/index/rebuild`

Полностью пересоздает индекс по текущему состоянию файловой системы.

```bash
curl -X POST "http://localhost:8080/index/rebuild"
```

Во время rebuild поиск временно блокируется. Это простая и предсказуемая стратегия для учебного проекта.

## Search Rules

Поиск выполняется через Bleve.

Текущие правила:

- Регистр не учитывается, потому что используется analyzer `standard`.
- Текст разбивается на поисковые термины analyzer’ом Bleve.
- Пунктуация в большинстве случаев работает как разделитель.
- Пустые токены отбрасываются.
- Для поля `content` используется text mapping с `Analyzer: "standard"`.
- Для `path` и `name` поля сохраняются, но не участвуют в общем полнотекстовом поиске.
- Несколько слов по умолчанию ищутся как AND: документ должен содержать каждое слово. `op=or` оставляет документ, если в нём есть хотя бы одно слово.

```text
GET /search?q=goroutine+scheduler&op=and
GET /search?q=goroutine+scheduler&op=or
```

- Ранжирование выполняет Bleve, значение `score` показывает относительную релевантность результата.
- Количество результатов ограничивается параметром `limit`, но не может превышать `maxLimit`.

Важно для исходного кода:

- `processRequest` индексируется как идентификатор согласно стандартному analyzer Bleve.
- Запрос `processRequest` должен находить такой идентификатор.
- Запрос `request` может не найти `processRequest`, если analyzer не разбил camelCase на отдельные части.
- `snake_case`, `foo.bar`, `package/name` обрабатываются по правилам стандартной токенизации Bleve.

## Document ID

ID документа - относительный путь от `rootDir`.

Например, для файла:

```text
sample-data/go/scheduler.md
```

при `rootDir = sample-data` ID будет:

```text
go/scheduler.md
```

Это удобно для обновлений:

- при создании или изменении файла вызывается индексирование с тем же ID;
- при удалении файла вызывается удаление документа по ID;
- если изменённый файл стал больше `maxFileSizeBytes`, документ с этим ID удаляется.

## Как работает индекс

При запуске сервис:

1. читает конфигурацию;
2. пересоздает индекс в `indexPath`;
3. подписывает watcher на `rootDir` и копит события, пока идёт обход;
4. рекурсивно обходит `rootDir`;
5. фильтрует файлы по расширению, размеру и ignored-директориям;
6. читает содержимое подходящих файлов;
7. передает документы в Bleve;
8. применяет события, которые пришли во время обхода.

Bleve строит inverted index. Упрощенно:

```text
document
  -> analyzer
  -> tokens
  -> inverted index
```

Поиск идет по индексу, а не через повторное чтение всех файлов.

## Автоматическое обновление индекса

После первичной индексации запускается watcher на основе `fsnotify`.

Схема:

```text
filesystem event
  -> debounce
  -> update queue
  -> workers
  -> Bleve index
```

Поддерживаются:

- создание файла;
- изменение файла;
- удаление файла;
- переименование файла как удаление старого пути и индексирование нового пути, если ОС/редактор присылает соответствующие события;
- переименование папки удаляет все документы со старым префиксом пути и индексирует файлы уже в новом дереве.

Debounce нужен потому, что одно сохранение файла может породить несколько событий: `WRITE`, `CHMOD`, `RENAME`, `CREATE`. Каждое такое событие заново ждёт тишину `debounceMs`, чтобы в индекс попала уже последняя версия файла. Если события идут без этой паузы, накопленные пути всё равно уходят в очередь не позже чем через `2 * debounceMs`.

Один и тот же файл всегда обрабатывает один и тот же воркер: путь попадает в его очередь. Две задачи этого пути не выполняются одновременно и не обгоняют друг друга. Разные файлы воркеры по-прежнему обрабатывают параллельно.

## Graceful Shutdown

Приложение обрабатывает `SIGINT` и `SIGTERM`.

При завершении:

1. HTTP-сервер перестает принимать новые запросы;
2. watcher завершается через общий context;
3. очередь обновлений закрывается;
4. workers завершают работу;
5. Bleve index закрывается.

## Тесты

Запуск:

```bash
go test ./...
go test -race ./...
```

Сейчас покрыты:

- первичное индексирование только поддерживаемых файлов;
- поиск по индексу, в том числе `op=and` и `op=or`;
- обновление одного документа и удаление из индекса;
- файл больше лимита уходит из индекса;
- создание, изменение, удаление и переименование файла через watcher;
- переименование папки;
- debounce: пачка записей даёт одну индексацию;
- конкурентный поиск во время обновления файлов.

## Замеры

Корпуса `sample_data/100`, `sample_data/1000` и `sample_data/5000`: в каждом файле 1 МиБ текста. Поиск — среднее по 20 запросам `scheduler`. Размер индекса — папка Bleve на диске.

| Файлов | Время индексации | Объём данных | Размер индекса | Средний поиск |
| --- | --- | --- | --- | --- |
| 100 | 8.5 с | 100 МиБ | 444 МиБ | 133 мс |
| 1000 | 1 мин 21 с | 1000 МиБ | 4.1 ГиБ | 277 мс |
| 5000 | 7 мин 18 с | 5000 МиБ | 10.8 ГиБ | 897 мс |

На 5000 файлах обновление одного документа заняло 94 мс, полный rebuild — 7 мин 27 с. Индекс хранит уже разобранные документы, поэтому менять один документ быстрее, чем заново читать и индексировать все 5000 файлов.

Повторить замер: `go run ./cmd/bench`. Сравнение одного файла и rebuild на уже собранном индексе 5000: `go run ./cmd/bench update`.
